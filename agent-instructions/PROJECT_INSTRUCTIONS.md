# Puzzpool Project Instructions

These instructions supplement the installed role contract and the current
WorkPackage. They do not weaken identity, permission, evidence, review, or
workflow-routing rules. When a typed WorkPackage conflicts with this document,
the WorkPackage wins.

## Repository and delivery model

- `main` is production. `dev` is the integration branch deployed to the test
  environment.
- Start agent-authored implementation branches from the current `dev` branch
  and target their pull requests back to `dev`. Never commit directly to
  `main` or `dev`; promotion from `dev` to `main` is a separate, tested release
  step.
- Preserve the recursive Git submodules under `third_party/`. Initialize them
  when a build checkout does not already contain them; do not replace vendored
  dependencies with ad-hoc copies.
- Keep commits and pull requests scoped to one issue. Do not mix deployment,
  generated output, or local database state into a product change.

## Architecture boundaries

- The backend is C++20 with Crow. `PoolService` is the HTTP boundary:
  parse the request, acquire the service lock when shared state is involved,
  delegate to domain code, and serialize the result.
- Keep allocation and submission behavior in `WorkService`,
  `SubmissionService`, and `Allocator`, without Crow dependencies, so it
  remains directly testable against in-memory SQLite.
- Preserve the dependency direction documented in `docs/architecture.md`:
  `main -> service -> {work_service, submission_service} -> allocator -> db ->
  config -> env`. Do not introduce cycles or move domain decisions into route
  handlers.
- Keep blocking network I/O and expensive computation outside the
  `PoolService` mutex. Read the required state while locked, release the lock
  for external work, then reacquire it only to validate and persist the result.
- The TypeScript sources under `frontend/` are the only authored frontend.
  `public/index.html` is generated by Vite, served by the C++ process, ignored
  by Git, and must never be edited or committed.

## Keyspace and allocator invariants

- Key ranges are half-open: `[start, end)`. Preserve this convention in
  allocation, submission validation, API documentation, and tests.
- Keyspace arithmetic is 256-bit. Use Boost Multiprecision `cpp_int`; do not
  narrow key counts, cursor values, virtual-chunk indexes, or range bounds to
  JavaScript numbers or fixed-width C++ integers.
- Persist and expose hexadecimal keyspace values as lowercase, zero-padded
  64-character strings.
- Transport values that may exceed JavaScript's safe integer range as decimal
  strings. Parse them with `BigInt` in the frontend; never use `Number()` or
  `parseFloat()` for these fields.
- Preserve deterministic full coverage: issued virtual-chunk runs must remain
  bounded, non-overlapping, and reproducible for the same puzzle and seed.
  Store one `chunks` row per issued job run, not one row per virtual chunk.
- Preserve the chunk lifecycle
  `assigned -> reclaimed/completed/FOUND`, heartbeat-based reclaim timing, and
  late-`FOUND` acceptance through `prev_worker_name`. Changes to these paths
  require direct regression tests.

## SQLite and persistence

- SQLite access uses SQLiteCpp, prepared/parameterized statements, WAL mode,
  and the service's synchronization model. Never construct SQL from
  worker-supplied, admin-supplied, or URL values.
- Scope puzzle-owned data by `puzzle_id`; scope worker-owned updates by both
  the row identifier and `worker_name` where ownership is required.
- Treat allocation, reclaim, completion, and finding persistence as atomic
  state transitions. Cover competing workers, retries, duplicate submissions,
  and late results when changing these paths.
- Schema evolution belongs in `PoolDb::migrate()`. Migrations must be
  idempotent on both a fresh database and an existing pre-migration database,
  with backfill behavior tested. Do not require operators to delete `pool.db`
  to adopt a schema change.
- Component tests must use the `:memory:` configuration from
  `tests/test_helpers.hpp`. Do not read, write, or depend on an operator's
  `pool.db`.

## HTTP and frontend contracts

- Keep HTTP request validation and status/error behavior explicit. Test both
  accepted and rejected forms whenever a route contract changes.
- Update `docs/api.md` in the same change as any route, request, response,
  status-code, or numeric-representation change.
- Keep `frontend/src/types.ts`, serialization in
  `src/service_serialization.cpp`, API documentation, and response-shape tests
  synchronized.
- Prefer `textContent` for untrusted values. When structured markup requires
  `innerHTML`, pass every worker-, puzzle-, or finding-derived string through
  the shared `esc()` helper.
- Preserve accessible names, roles, focus behavior, and `aria-pressed` state.
  Update `frontend/src/accessibility.test.ts` when dashboard controls or filter
  groups change.
- Keep polling and rendering work bounded. Changes to canvas rendering,
  dashboard polling, or large collections require a regression or performance
  test that would fail if the expensive behavior returns.

## Security and local state

- Admin routes must remain behind the central admin-token check and the
  documented Nginx restriction. Never expose an admin mutation through an
  unguarded route.
- Worker names are intentionally unauthenticated, but a worker must not be
  able to complete another worker's assigned job.
- Never commit or print `.env`, `ADMIN_TOKEN`, database files, WAL/SHM files,
  or `BINGO_FOUND_KEYS.txt`. Do not place real discovered private keys in
  fixtures, logs, review reports, or issue comments.
- Do not weaken the Node.js minimum-release-age guard in CI or production.
  `MINIMUM_NODE_RELEASE_AGE=0` is acceptable only for an explicitly local
  development run.

## Documentation

Update the document that owns the changed contract:

- `docs/api.md` for API shapes and behavior;
- `docs/database.md` for schema, migrations, indexes, and lifecycle changes;
- `docs/architecture.md` for components, dependencies, concurrency, and data
  flow;
- `docs/security.md` for trust-boundary or dependency-supply-chain changes;
- `docs/testing.md` for test commands, fixtures, and verification strategy;
- `README.md` and `.env.example` for setup, deployment, or configuration
  changes.

Puzzpool does not maintain a changelog; do not invent one for an ordinary
change.

## Verification

Run focused tests while developing, then the complete relevant suite before
handoff.

Backend:

```bash
cmake -S . -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DPUZZPOOL_BUILD_TESTS=ON
cmake --build build --parallel "${BUILD_JOBS:-1}"
ctest --test-dir build --output-on-failure
```

Frontend:

```bash
npm test --prefix frontend
npm run build --prefix frontend
```

Also run:

```bash
bash tests/test_check_node_version_age.sh
```

- Use `npm ci --prefix frontend` when dependencies are absent or the lockfile
  changed and the execution profile permits network access.
- Run the local-server smoke test from `docs/testing.md` when route wiring,
  startup, configuration, database initialization, or the generated dashboard
  changes.
- Run the skipped permutation benchmark explicitly when changing permutation
  or allocator performance; do not treat it as part of ordinary CTest.
- Report exact commands and results. Do not claim the full suite passed when
  only a focused subset ran.
